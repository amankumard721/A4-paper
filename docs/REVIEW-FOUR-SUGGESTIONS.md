# Review of four suggestions — 10 October 2026

1. **Image size: implemented with JPEG 85 for opaque photos.** Alpha images and explicitly selected signatures remain lossless PNG. Existing PNG IDs keep working. Both the private asset route and editor validate PNG/JPG UUID names; the PDF exporter directly embeds JPEG bytes (DCTDecode), avoiding a PNG conversion. WebP is not selected because the current pdf-lib image path supports JPEG/PNG directly. Lossy compression is not quality-neutral, and a fixed 5 MB → 500 KB saving cannot be promised. WEBP_LOSSY also needs API 30 while this app supports API 26.
2. **Orphan cleanup: implemented conservatively at startup.** After successful document recovery, an IO scan reads content references from every saved document and every export-request snapshot, including atomic backups. A failed scan deletes nothing. Only unreferenced UUID PNG/JPG files older than 24 hours are eligible. One scan per process before editing protects live undo history and new imports. Duplicate documents and pending exports protect shared files. Deleting one document does NOT immediately delete its images. Reclamation occurs on a later app process startup after the grace period; it is not periodic while the app remains open. Existing malformed snapshots conservatively postpone cleanup. Temporary/unknown files are not removed by this collector.
3. **Repeated parsing: removed from MainViewModel.edit.** The UI checks size and queues the latest immutable content. The coalescing save queue runs repository serialization on Dispatchers.IO; the parsed content object is validated and walked once, then reused for the saved JSON envelope. Validation precedes AtomicFile.startWrite, so invalid content cannot replace the saved original. Flush surfaces save failures. Regex was rejected: it can match JSON-looking text, misses escaped keys/values, does not validate nesting or document structure, and the claimed universal 100× speedup is unsupported. The existing JS-to-native bridge still parses its incoming envelope; this change does not claim zero main-thread work.
4. **Large boot payload: implemented as a small origin-targeted postWebMessage containing a per-load local URL.** WebView fetches JSON through an in-memory WebViewAssetLoader response on its request thread. Full document JSON is no longer interpolated into evaluateJavascript. The route uses a per-load UUID, local HTTPS origin and no-store; remote requests and frames remain blocked. No world-readable payload file is created. This avoids sending an entire document as a bridge message, but does not promise unlimited memory or crash immunity. Small toolbar commands still use evaluateJavascript. Native WebView delivery requires physical-device verification; desktop tests simulate the inbound message and exercise the fetch/boot/JPEG export path.

Validation: AssetReferenceTest covers JPEG IDs, escaped JSON keys, malformed JSON and cleanup retention; editor/tests/review.test.mjs checks streamed boot and direct JPEG embedding; existing browser regressions and Android build/unit/lint tasks are run for this delivery. See TEST-RESULTS.md for exact status.
